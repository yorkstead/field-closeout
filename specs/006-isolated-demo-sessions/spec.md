# Feature: Isolated demo sessions and locked-down reset

**Spec:** `specs/006-isolated-demo-sessions/` · **Status:** Draft
**Owner gate:** Brandon approves this spec and resolves all Open decisions before plan/tasks are handed to an implementer.

## Problem and outcome
As Brandon walking a prospect through the hosted demo, I want each visitor to receive an independent copy of the fictional Northstar data and to reset only that copy, so that simultaneous prospect calls neither expose one another's change orders nor allow one caller to wipe another caller's demo.

Today `field-closeout.vercel.app` uses one shared Postgres demo dataset, has no login, and exposes **Reset Demo** through `POST /api/demo/reset` and `src/components/DemoHeader.tsx`. The outcome is server-enforced isolation for `hosted_demo`, bounded retention of demo data, and no behavior change in `protected_pilot`.

## Scope
### In scope
- Provision an isolated demo tenant and its Northstar seed records automatically on a visitor's first `hosted_demo` visit under recommended Option A below. Repeated visits with the same valid demo cookie resume the same tenant; a new browser/session receives a different tenant.
- Keep the version-controlled Northstar seed/template read-only to visitors. Generate all tenant-scoped records needed for the existing job, add-on, approval, closeout, and reconciliation flows; never copy mutable legacy visitor input or real customer data.
- Parameterize provisioning so every visitor receives newly generated/remapped primary and foreign keys, a globally unique tenant slug, and cryptographically random globally unique approval tokens. Do not reuse fixed fixture UUIDs or predictable tokens across visitor tenants; compute seeded snapshot hashes from newly generated change-order IDs. Preserve six catalog items, four jobs, and three baseline change orders unless separately changed. The canonical local fixture may retain stable test IDs/data, but its seeded approval tokens must also become random, with tests looking them up rather than hardcoding them.
- Establish tenant context exclusively on the server from an opaque, unguessable, `httpOnly` demo-session cookie. Never accept a tenant or demo-session identifier from a query, body, client header, or client tenant switcher as authority.
- Constrain every existing session-scoped demo read and mutation, including role-switched tech/office views and `POST /api/demo/reset`, to the caller's server-resolved demo tenant. A requested record belonging to another demo tenant is indistinguishable from a missing record.
- Reset only the caller's tenant in a transaction: remove that tenant's current demo records, restore the Northstar baseline, and leave sibling visitors, the canonical template, and unrelated runtime modes untouched. A failed reset leaves the caller's prior data intact.
- Preserve `/approve/[token]` as a zero-login, single-change-order capability. A valid token works without a demo cookie and on the tech's phone; it exposes only the approved customer-facing scope and never becomes a tenant-selection or reset mechanism. Resetting the owning demo tenant invalidates that tenant's old approval tokens.
- Expire and clean up old demo tenants and all owned records. Recommended: absolute expiry seven days after provisioning, with bounded lazy cleanup only during first-visit provisioning so no new paid service, scheduler, or secret is required. Reset never cleans up other visitors. Expired sessions must not resume even if physical deletion has not run.
- Add an ordered schema migration for session/retention metadata and required keys/indexes. Run `bun run db:migrate:check`; document code and data rollback.
- Add regression coverage for independent sessions, cross-tenant attempts, reset, cleanup/expiry, public approval, and runtime guards while preserving all existing tests.

### Out of scope (non-goals)
- Real accounts/authentication, self-serve signup, prospect attribution/analytics, or blocked `004` pilot-auth work.
- Any change to real tenant isolation or `protected_pilot` behavior beyond proving existing demo hard-disables remain intact.
- Payments, sales-tax calculation, legal/tax advice, SMS/email sending, live QuickBooks/FSM integration, or any expansion beyond Change-Order Record Only.
- Per-prospect link administration under recommended Option A; this is the compared alternative, not an additional deliverable.
- A new paid service, external worker, cron secret, production migration, deploy, Vercel/GitHub configuration change, or customer contact. Brandon separately gates any later production migration/deploy.
- Real PII or license pricing.

## Acceptance criteria
- AC1 — Given two clean browser contexts visiting `field-closeout.vercel.app` in `hosted_demo`, when each creates a differently named fictional change order and navigates the existing tech/office views, then each sees only its own Northstar copy and its own change order; neither dashboard, queue/KPIs, summary, CSV export, nor existing API response contains the other's records (apart from a single record deliberately opened through its valid `/approve/[token]` URL).
- AC2 — Given sessions A and B each have modified their own demo, when A selects **Reset Demo**, then A returns to the Northstar baseline and B's jobs, line items, totals, statuses, approval events, approval tokens, and reconciliation references remain byte-for-byte unaffected; a simultaneous B reset affects only B.
- AC3 — Given session A and a valid tenant/job/change-order identifier belonging to B, when A supplies that identifier to a record-addressed page/API, then it returns identical not-found status/body behavior to an absent record (preserving each existing route's current not-found semantics rather than imposing 404) without reading/mutating B or appending an event. Given B identifiers injected as selectors into role-switch, reset, or bootstrap requests, when the server processes them, then it rejects the request without mutation and never looks up B to decide; server-resolved tenant scope cannot be overridden.
- AC4 — Given a change order in isolated `hosted_demo` session A, when its homeowner approval URL is opened with no demo cookie on the tech's phone or another device, then the existing approve/decline and sign-on-glass flow works once without provisioning a visitor tenant, writes the immutable event and SHA-256 snapshot hash only to A's record, places no unrelated contractor session props, controls, internal links, or other A/B records in HTML/RSC, and keeps token-derived branding/disclaimer; an on-device return-to-tech link appears only when the cookie-resolved tenant matches the token owner, and after A resets the old token no longer resolves.
- AC5 — Given `APP_RUNTIME_MODE=protected_pilot`, when any demo provisioning, role-switching, reset, cleanup, or demo-cookie path is requested, then no demo tenant/session is created and role switching/reset remain hard-disabled; existing protected-pilot reads, authorization behavior, and approval-page/header/on-device-link rendering are unchanged. Given `APP_RUNTIME_MODE=local`, when existing local workflows run, then deterministic shared-tenant seed/reset behavior and stable test IDs remain available, with only approval-token values changed to mandatory random values and tests using dynamic lookup.
- AC6 — Given demo sessions on both sides of the approved retention boundary (recommended: provisioned more than seven days ago), when expiry is checked on access or bounded cleanup runs during first-visit provisioning, then expired cookies cannot resume old data, only expired demo tenants and their owned rows are deleted, recent demo tenants and the canonical template remain intact, cleanup is bounded per invocation, reset invokes no cleanup, and no scheduler, paid service, or new secret is invoked.
- AC7 — Given a local Postgres database at the prior migration, when the ordered migration is applied and `bun run db:migrate:check` runs, then the check passes and seed/migration order is reproducible; when the documented rollback is rehearsed locally, then the prior application revision still works without deleting non-demo data.
- AC8 — Given the completed implementation on the tested revision, when `bun run verify` and the existing unit and e2e suites run, then all pass, including the new two-context isolation/reset tests and runtime/public-token regression tests, with real output recorded in `verification.md`.
- AC9 — Given a failed copy or reset at any point in its transaction, when the request completes, then no partial Northstar copy or partially reset caller tenant is visible and all other sessions remain available.
- AC10 — Given a new browser that first opens an allowlisted internal URL directly, when hosted bootstrap completes, then it sets only the new secure demo-session credential plus any chosen role, creates one complete isolated baseline, and never renders canonical/shared data as an intermediate response; reloads, multiple tabs, and tech/office role switches retain that visitor tenant. Given a missing, forged, invalid, or expired credential, when an internal page or API is requested, then it bootstraps a fresh visitor or rejects the request as appropriate and never falls back to canonical data; `/approve/*`, health, and static requests create no visitor.

## Constraints and compatibility
- Existing behavior to preserve: the complete Phase 1 field-capture → threshold/office-review → homeowner-decision → closeout → printable/exportable-summary → manual-reconciliation flow; integer-cent totals; immutable approved/declined/reconciled records; append-only approval events; scoped idempotent approval tokens; role authorization; local development workflow; and every `protected_pilot` guard.
- Data, money, and security rules that apply (see `AGENTS.md`): tenant and role scope are server-side only; money stays integer cents and is recalculated server-side; copied/reset records retain the same invariants as newly entered records; all committed data/screenshots remain fictional Northstar data. The approval-token capability is the only intentional cross-browser route to a demo change order and remains limited to that record's customer-facing decision scope. Visitors can enter arbitrary text/photos, so retention must treat all visitor data as potentially sensitive even though real PII is prohibited.
- Owner-gated effects (customer-visible change, production, migrations, external writes): this spec authorizes local implementation and tests only after approval. Brandon must separately approve and perform/gate the hosted migration and deployment. No hosted database is touched by implementation or verification without that approval.
- Rollback: use an additive, backward-compatible `0003` migration and leave session mappings/data in place; there is no existing down-migration command. Rolling back to prior application code is technically compatible but reopens shared-canonical demo behavior, so Brandon must explicitly choose between pausing the hosted demo (recommended) and temporarily accepting that known risk. Do not drop the session table or delete visitor/canonical rows as an implicit rollback. Any destructive down migration, legacy reset/deletion, or expired-data deletion against hosted storage requires separate local rehearsal, backup/restore planning, and Brandon's explicit approval; non-demo data must never be removed.
