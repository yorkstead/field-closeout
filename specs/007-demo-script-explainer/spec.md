# Feature: Ten-minute demo script and one-page explainer

**Spec:** `specs/007-demo-script-explainer/` · **Status:** Draft
**Owner gate:** Brandon approves this spec and resolves all Open decisions before plan/tasks are handed to an implementer.

## Problem and outcome
As Brandon demonstrating Field Closeout to HVAC and plumbing contractors, I want a repeatable ten-minute phone walkthrough and a concise public explainer, so that a prospect can understand the complete fictional add-on approval and closeout workflow without mistaking the Phase 1 demo for a payment, tax, legal, messaging, or accounting-integration product.

## Scope
### In scope
- Create `docs/sales/demo-script.md` as an exact, spoken run-of-show for the existing hosted demo. Setup/reset is a preflight step outside the timed run; the timed segments below total exactly **10:00 (600 seconds)** with no gap or overlap.

| Time | Duration | Required demonstration |
|---|---:|---|
| 0:00–0:40 | 40s | Hook, Northstar fictional-data warning, live-demo orientation, and Change-Order Record Only boundary. |
| 0:40–2:20 | 100s | As Tech Marcus, open `JOB-2026-104` for fictional Casey Vance, add **Replace Corroded Shutoff Valve — $180**, and submit directly for homeowner approval because $180 is at or below the $500 demo threshold. |
| 2:20–4:00 | 100s | Select **Hand Phone to Homeowner**, have Casey sign on the tech's phone, show the approved receipt and tamper-evident snapshot, then return to the tech view. |
| 4:00–6:10 | 130s | As Office Dana, use the closeout queue, show the printable Closeout Summary, use **Print / Save PDF**, and **Mark Reconciled** to fictional `INV-4821`; use the print/reconcile order chosen in D4 and narrate the status visible at that moment. |
| 6:10–8:40 | 150s | Capture the D3 **$650** add-on, show that it exceeds the $500 threshold and goes to office review rather than the homeowner, then as Dana use **Review & Release** and show **Awaiting Homeowner**. The second homeowner signature is not repeated. |
| 8:40–10:00 | 80s | HVAC/plumbing value recap, answers to the priority objections, and a pointer to the public explainer/demo link. |

- Make the script executable without invented UI: use the existing labels **Hand Phone to Homeowner**, **Print / Save PDF**, **Mark Reconciled**, and **Review & Release**, the existing fictional people/job/catalog data, and invoice reference `INV-4821` as a manual record only. Include preflight and a brief recovery note for a missed click without extending the timed script. Reset only in local or a verified caller-isolated environment: until Spec 006 or equivalent caller-isolated reset is deployed, the script must explicitly forbid resetting or using the shared hosted demo for a prospect run; local/LAN or separately isolated preview acceptance may proceed independently (D6).
- Include trade-specific talking points for HVAC and plumbing and concise objection answers. Cover at least: capturing a mid-job add-on before it is forgotten, zero-login/on-device approval, office control above a tenant-configurable threshold, and a printable approval/reconciliation record for the existing invoicing process.
- State explicitly in the script and explainer that Phase 1 does **not** process payments, calculate sales tax, provide legal or tax advice, send SMS/email, synchronize/write to QuickBooks or another FSM, or provide self-serve signup. Share links are copied manually; final tax and invoicing stay in the contractor's existing tool; `INV-4821` does not create or send an invoice.
- Add one self-contained, phone-readable public explainer at `/how-it-works`, using the recommended static-file approach in D1. Explain the three-part field → homeowner → office workflow, label the application and every example as fictional/demo material, and link to `https://field-closeout.vercel.app` for the live demo.
- Add `tests/e2e/demo-script.spec.ts` and `tests/e2e/how-it-works.spec.ts` so the documented labels, threshold flow, closeout flow, explainer route, demo link, required disclosures, and basic phone layout remain testable. Tests must locate records through visible fictional data/current responses rather than hardcoded approval tokens so they remain compatible with Spec 006 isolated demo sessions.

### Out of scope (non-goals)
- Changing field capture, approval, closeout, reconciliation, money, database, authentication, tenant, or runtime-mode behavior.
- A new Next.js app route under `src/app`, a second explainer source, a PDF asset, analytics, CRM/prospect tracking, customer contact, or commercial license pricing. Demo line-item amounts and the $500 demo threshold are workflow examples, not product/license pricing.
- Payment processing, sales-tax calculation, legal/tax advice or compliance claims, SMS/email providers, live QuickBooks/FSM integration, self-serve signup, real customer PII, or claims that these capabilities are included.
- Production deployment, hosted database operations, or changing the live deployment. Brandon separately gates any deployment after local verification and phone acceptance.
- Requiring Spec 006 for local implementation/tests or changing its design. The complete hosted prospect run is nevertheless release-blocked until 006 or equivalent caller-isolated reset is deployed; this change must not reintroduce fixed-token/shared-session assumptions or authorize a shared hosted reset.

## Acceptance criteria
- AC1 — Given `docs/sales/demo-script.md`, when its timed table is read from start to finish, then its segments are contiguous from `0:00` through `10:00`, sum to exactly 600 seconds, contain every required action in the required order, and leave reset/preflight outside the timed ten minutes.
- AC2 — Given a clean fictional demo and the $180 segment, when Marcus adds Replace Corroded Shutoff Valve to `JOB-2026-104` for Casey Vance and submits, then the existing server computes $180 in integer cents, routes directly to `pending_homeowner`, and the script selects **Hand Phone to Homeowner**, records Casey Vance's on-device approval, and shows a 64-character SHA-256 snapshot hash without a login or a second device.
- AC3 — Given the approved $180 change order and the D4 order selected at specification approval, when Dana follows the closeout segment, then the script shows the office queue and Closeout Summary, invokes **Print / Save PDF**, records `INV-4821` through **Mark Reconciled**, and accurately calls the summary **Unbilled** if printed before reconciliation or **Reconciled** with `INV-4821` if printed afterward; it never claims that an external invoice was created, sent, paid, or synchronized.
- AC4 — Given the D3 add-on totaling $650 and a tenant threshold of $500, when Marcus submits it, then it becomes `pending_office` and cannot be approved by the homeowner before office release; when Dana selects **Review & Release**, then it becomes `pending_homeowner`/**Awaiting Homeowner**, with the existing audit events and no client-supplied total trusted.
- AC5 — Given the talking-points and objection sections, when a prospect asks about HVAC or plumbing use, payments, tax, legal effect, texting/email, or QuickBooks/FSM sync, then the script supplies a plain-language answer consistent with the Phase 1 boundary and existing invoicing workflow, without legal/compliance promises, invented customer results, or commercial license pricing.
- AC6 — Given no demo session cookie, when a visitor requests `/how-it-works`, then the targeted rewrite serves the self-contained `public/how-it-works.html` successfully without rendering `src/app/layout.tsx`, reading the session/Postgres for page content, showing contractor role switching/Reset Demo controls, or provisioning/resetting a demo tenant; `/how-it-works.html` remains a valid direct static asset.
- AC7 — Given the explainer on a phone-width viewport (at least 390×844), when Brandon reads and taps through it, then it has no horizontal overflow, has a clearly tappable link to `https://field-closeout.vercel.app`, identifies the demo and Casey/Northstar examples as fictional, summarizes tech capture → homeowner approval → office print/reconcile, and displays the Phase 1 payment/tax/legal/SMS/integration boundary without any commercial license price.
- AC8 — Given the finished branch and local test environment, when `bun run verify` runs, then the existing suites plus `demo-script.spec.ts` and `how-it-works.spec.ts` pass on the tested revision and real output is recorded in `verification.md`; the automated run need not wait ten real minutes, but must check the documented timeline arithmetic and actual UI transitions.
- AC9 — Given the finished script and explainer on an owner-accessible local/LAN, verified isolated preview, or post-D6 hosted URL, when Brandon reads both artifacts and performs the complete click-through on a physical phone, then he can finish the scripted flow in at most ten minutes, tap the explainer's demo link, reach the expected screens without presenter-only corrections, and record pass/fail, elapsed time, device/browser, URL, and any ambiguity in `verification.md`; automated tests do not replace this gate.
- AC10 — Given the final diff, when it is reviewed for data and commercial safety, then it contains only synthetic Northstar examples and fictional invoice references, no secrets or real PII, no commercial license pricing, no new external provider calls, and no application behavior beyond the additive static explainer and targeted rewrite.
- AC11 — Given the currently deployed shared canonical demo without Spec 006, when Brandon prepares a hosted prospect call, then the script's warning explicitly prevents a hosted reset or full hosted prospect run and directs him to local/isolated acceptance instead; only after caller-isolated reset is deployed and verified may the hosted preflight/reset and prospect walkthrough be used.

## Constraints and compatibility
- Existing behavior to preserve: the complete Phase 1 capture → threshold routing → dual-mode zero-login decision → immutable receipt → office queue → printable summary → manual reconciliation flow; existing roles, tenant configuration, exact server-side money, audit events, approval tokens, runtime guards, and all current tests. The $500 threshold is the fictional Northstar default, not a universal contractor rule.
- Data, money, and security rules that apply (see `AGENTS.md`): all names, job numbers, photos, amounts, and invoice references in committed artifacts are fictional; money remains integer cents and server-authoritative; approved/reconciled records remain immutable; `/approve/[token]` remains single-order and idempotent. Public static content must not expose tokens, internal records, session data, secrets, or real PII.
- Owner-gated effects (customer-visible change, production, migrations, external writes): spec approval authorizes only the listed local docs/static/test work. The explainer is customer-visible when deployed, so merge and especially production deployment remain Brandon's gates. No hosted migration, hosted reset/seed, external write, or customer contact is authorized.
- Rollback: revert the additive docs, static HTML, targeted rewrite, and tests. No schema or data rollback is required; removing `/how-it-works` does not alter existing application routes or records.
